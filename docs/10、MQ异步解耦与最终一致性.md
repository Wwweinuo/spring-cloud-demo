# 10-MQ 异步解耦与最终一致性

> 本文是《Java 后端微服务学习计划》的优先级 10 专题。
>
> RabbitMQ 和 RocketMQ 选择一个深入即可。本文以 RabbitMQ 的通用消息模型说明，具体客户端和部署配置以项目最终选型为准。

## 一、本阶段学习目标

- 判断哪些工作适合从同步请求中异步化。
- 理解生产者、交换机、队列和消费者的关系。
- 处理消息确认、消费失败、重试、死信和积压。
- 通过幂等消费应对重复消息。
- 使用消息驱动流程实现最终一致性。

## 二、为什么需要消息队列

同步调用会把所有工作放在用户请求的等待时间内：

```text
创建订单
  ├── 写订单
  ├── 发送通知
  ├── 增加积分
  └── 更新统计
        ↓
      用户一直等待
```

消息队列可以把不需要立即返回的工作异步化：

```text
订单服务
  ├── 写入订单
  └── 发布 OrderCreated
          ↓
         MQ
      ┌───┼────┐
通知服务 积分服务 统计服务
```

消息队列提高了解耦和削峰能力，但也引入了消息丢失、重复、乱序、积压和最终一致性问题。

## 三、消息模型

| 角色 | 职责 |
| --- | --- |
| Producer | 发布业务事件 |
| Exchange / Topic | 按规则分发消息 |
| Queue / Subscription | 保存待消费消息 |
| Consumer | 处理业务并确认消息 |
| Dead Letter | 保存多次失败消息 |

消息内容应包含事件类型、业务 ID、事件 ID、发生时间和必要的业务数据：

```json
{
  "eventId": "evt-20260831-001",
  "eventType": "OrderCreated",
  "orderId": 1001,
  "occurredAt": "2026-08-31T10:00:00+08:00"
}
```

不要把整个数据库实体无边界地序列化到消息中。消息契约需要版本管理和兼容策略。

## 四、CloudMall 实践：订单超时取消

目标流程：

```text
创建待支付订单
  ↓
发布订单超时事件
  ↓
延迟到期后消费
  ↓
查询订单状态
  ├── 已支付 → 不处理
  └── 未支付 → 取消订单并恢复库存
```

消费前必须再次查询订单状态，不能仅凭消息认定订单仍未支付。取消和恢复库存要设计幂等，避免重复消费导致重复恢复。

## 五、可靠投递和消费确认

生产端需要考虑：

- 业务数据提交成功但消息发布失败。
- 消息发布成功但业务事务回滚。
- 网络异常导致发布结果未知。

常见方案包括本地消息表、Outbox、事务消息和可靠投递重试。选择方案时应先明确一致性要求，不要把 MQ 的“发送成功”当成业务事务完成。

消费端需要考虑：

```text
收到消息
  ↓
执行业务
  ├── 成功 → ACK
  └── 失败 → 重试 / NACK / 死信
```

只有业务处理成功后才确认消息。对确定性的参数错误不能无限重试，应直接进入死信并告警。

## 六、重复消费和幂等

消息至少一次投递时，重复消费是正常情况。消费者可以使用 `eventId` 做幂等记录：

```text
eventId 是否已处理？
  ├── 是 → 直接确认消息
  └── 否 → 执行业务 → 记录成功 → 确认消息
```

幂等记录和业务变更最好处于同一个本地事务中，或使用唯一索引保证并发下只有一次成功处理。只在内存中保存已处理 ID，服务重启后会失效。

## 七、故障实验

### 实验 1：消费者处理失败

让消费者前几次处理失败，观察重试次数、重试间隔和最终死信结果。

### 实验 2：重复消息

手动投递相同 `eventId` 两次，确认订单取消或库存恢复只执行一次。

### 实验 3：消费者停机和积压

停止消费者并持续生产消息，再恢复消费者，观察队列长度、消费速度和系统资源。

### 实验 4：业务成功但 ACK 丢失

模拟业务已提交、确认消息失败的情况，确认重复消息不会造成重复业务操作。

## 八、同步和异步的取舍

适合异步化：通知、积分、统计、日志、订单超时检查等不需要立即返回结果的工作。

不应盲目异步化：需要立即确认价格、库存和权限的核心校验。异步化后，用户看到的可能只是“处理中”，系统还要提供查询状态和失败补偿能力。
