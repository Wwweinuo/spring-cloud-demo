# 11-可观测性：日志、指标与链路追踪

> 本文是《Java 后端微服务学习计划》的优先级 11 专题。

## 一、本阶段学习目标

- 区分日志、指标、链路追踪和健康检查。
- 为一次跨 Gateway、订单、商品和用户服务的请求建立 TraceId。
- 使用 Actuator 暴露健康状态和基础指标。
- 设计接口成功率、延迟、错误率和依赖状态指标。
- 从证据出发定位慢调用和故障，不依赖猜测。

## 二、为什么需要可观测性

用户只看到“下单很慢”，但真实耗时可能来自：

```text
Gateway 200ms
  ↓
Order Service 100ms
  ├── User Service 50ms
  ├── Product Service 3s
  └── MySQL 200ms
```

没有统一的请求标识和时间记录，只能在多个服务日志中人工猜测。可观测性要回答三个问题：系统发生了什么、现在是否健康、一次请求经过了哪里。

## 三、四类观测信号

| 信号 | 适合回答的问题 | 示例 |
| --- | --- | --- |
| 日志 | 发生了什么细节 | 订单 100 创建失败 |
| 指标 | 整体趋势怎样 | P95 延迟升高 |
| Trace | 一次请求经过哪里 | 商品调用耗时 3 秒 |
| Health | 组件是否可用 | 数据库连接失败 |

四类信号要通过服务名、环境、实例、接口和 TraceId 关联起来。

## 四、TraceId 传播

```text
客户端
  X-Trace-Id: abc123
      ↓
Gateway 记录 abc123
      ↓ HTTP Header
Order Service 记录 abc123
      ↓ Feign Header
Product Service 记录 abc123
```

如果入口没有 TraceId，Gateway 可以生成一个；如果已有合法格式的 TraceId，可以继续传播。不能把用户可控的超长或非法值无校验地写入日志。

日志至少包含：

```text
timestamp service traceId instance method path status duration error
```

生产环境建议使用结构化 JSON 日志，避免只依赖拼接字符串。

## 五、指标设计

建议先关注少量有行动价值的指标：

- 请求总数和成功数。
- HTTP 4xx、5xx 数量。
- P50、P95、P99 延迟。
- Feign 下游调用次数、失败数和超时数。
- JVM 内存、线程和 GC。
- 数据库连接池使用率。
- MQ 队列积压量。

指标标签不能包含订单 ID、用户 ID 等高基数字段，否则会产生大量时间序列，增加监控成本。

## 六、Actuator 基础检查

Gateway 当前暴露了：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info
```

基础验证：

```bash
curl http://localhost:8000/actuator/health
```

健康检查应区分：

- 进程是否存活。
- 服务是否已准备好接收流量。
- 关键依赖是否可用。

不能为了让监控“显示 UP”而隐藏关键数据库或配置中心故障。

## 七、慢调用定位实验

1. 为商品服务增加 3 秒可控延迟。
2. 从 Gateway 发起订单请求。
3. 在 Gateway、订单服务和商品服务日志中搜索同一个 TraceId。
4. 对比每一段的开始时间、结束时间和耗时。
5. 查看订单接口 P95 延迟和 Feign 超时数量。
6. 恢复延迟开关，确认指标逐渐恢复。

实验记录应包含证据：请求 URL、TraceId、各服务耗时、异常类型和恢复时间。

## 八、告警思路

告警不应只监控 CPU。可以从以下条件开始：

```text
5xx 比例持续升高
P95 延迟超过阈值
Feign 超时持续增加
Nacos 注册实例数异常减少
MQ 积压持续增长
数据库连接池接近耗尽
```

阈值需要结合基线和持续时间，避免短暂抖动造成告警风暴。

## 九、通过标准

- [ ] 能区分日志、指标、Trace 和健康检查。
- [ ] 能让 TraceId 穿过 Gateway、订单和商品服务。
- [ ] 能通过日志证据找出慢调用位置。
- [ ] 能解释 P95/P99 和错误率的意义。
- [ ] 能为服务和依赖设计基础指标。
- [ ] 能说明高基数标签为什么会造成监控问题。
