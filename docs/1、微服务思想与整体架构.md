# 1-微服务思想与整体架构

> 本文是《Java 后端微服务学习计划》的第一个专题。
>
> 本阶段的目标是建立微服务的整体认知，并搭出可以独立启动的多模块项目骨架。本阶段暂不引入 Nacos、OpenFeign、Gateway、Sentinel、Seata 等治理组件，先把“为什么拆、如何拆、拆完以后谁负责什么”想清楚。

## 一、本阶段学习目标

完成本阶段后，应该能够：

- 解释单体架构和微服务架构的核心区别。
- 说明为什么要拆分服务，以及微服务带来的额外复杂度。
- 按业务边界划分 `user-service`、`product-service` 和 `order-service`。
- 为每个服务明确数据所有权和职责边界。
- 创建一个 Maven 多模块项目，让三个服务能够独立启动。
- 画出客户端、业务服务、基础设施和后续治理组件的关系。
- 解释一次业务请求在单体和微服务中的处理差异。
- 识别服务拆分中的常见错误，并能说明改进方式。

## 二、先建立整体认知

### 2.1 单体架构是什么

单体应用通常把用户、商品、订单等模块放在同一个应用中：

```text
客户端
  ↓
一个 Spring Boot 应用
  ├── 用户模块
  ├── 商品模块
  ├── 订单模块
  └── 数据访问模块
        ↓
      MySQL
```

单体并不等于低级架构。对于业务规模小、团队人数少、部署要求简单的系统，单体架构通常更容易开发、测试和部署。

单体架构真正需要关注的问题不是“好不好”，而是它是否已经无法满足当前的业务和团队需求，例如：

- 一个模块的发布必须带着整个应用一起发布。
- 某个热点模块扩容时，只能扩容整个应用。
- 不同模块的技术栈和依赖版本相互影响。
- 一个模块的内存泄漏或线程耗尽可能拖垮整个应用。
- 团队成员修改同一个大工程时，协作和交付成本逐渐增加。

### 2.2 微服务架构是什么

微服务架构将一个较大的业务系统拆分为多个相对独立的服务。每个服务围绕一组明确的业务能力构建，能够独立开发、测试、部署和扩容。

```text
客户端
  ├──→ user-service
  ├──→ product-service
  └──→ order-service

每个服务：
  ├── 独立进程
  ├── 独立代码边界
  ├── 独立发布能力
  └── 对自己的业务数据负责
```

微服务的重点不是“服务越多越好”，而是让服务边界与业务边界相对一致，并让团队能够用可接受的成本管理分布式系统的复杂度。

### 2.3 单体和微服务的对比

| 对比项 | 单体架构 | 微服务架构 |
| --- | --- | --- |
| 部署 | 整体部署 | 服务可独立部署 |
| 扩容 | 通常整体扩容 | 可以按热点服务扩容 |
| 调用 | 多为进程内调用 | 需要网络调用或消息 |
| 事务 | 本地事务较容易处理 | 需要处理跨服务一致性 |
| 数据 | 容易共享表和事务 | 服务应拥有自己的数据边界 |
| 故障 | 容易整体受影响 | 可以隔离，但也可能发生级联故障 |
| 运维 | 组件较少，管理简单 | 需要注册、配置、监控和日志治理 |
| 团队协作 | 代码集中，容易互相影响 | 边界清晰，但需要接口契约和协作规范 |
| 适用场景 | 业务规模较小或早期探索 | 业务复杂、团队扩大或需要独立演进 |

## 三、为什么要拆分微服务

服务拆分通常由以下问题驱动，而不是为了追赶技术潮流。

### 3.1 独立发布

商品服务的修改不应该因为订单服务没有变化而被迫一起发布。独立发布可以缩小变更范围，降低回归和上线风险。

### 3.2 独立扩容

如果商品查询流量远高于用户查询，应该能够只扩容商品服务，而不是把整个单体应用复制多份。

### 3.3 故障隔离

库存服务出现慢查询时，理想情况下不应该直接拖垮用户服务和商品服务。服务化为限流、超时、熔断和降级提供了边界。

注意：拆成服务不会自动获得故障隔离。如果没有超时、线程池隔离、限流和监控，网络调用反而可能造成更严重的级联故障。

### 3.4 团队和代码边界

用户、商品和订单通常由不同业务人员负责。将边界体现在代码和服务中，可以减少互相修改内部实现的情况。

### 3.5 技术和数据独立演进

不同服务可能有不同的性能、存储或发布需求。服务边界清晰后，才有机会在不影响全局的情况下进行技术演进。

## 四、拆分后新增的复杂度

学习微服务不能只记优点，还要清楚它把哪些问题从代码内部转移到了系统层面。

### 4.1 网络调用不可靠

进程内方法调用通常很快且失败路径相对明确；网络调用会遇到：

- DNS 或服务地址错误。
- 网络抖动和连接失败。
- 响应超时。
- 服务已经收到请求，但调用方没有收到响应。
- 请求重试造成重复写入。

### 4.2 数据一致性更难

订单、库存和账户分散到不同服务后，一个本地事务无法覆盖所有数据库。后续需要学习分布式事务、消息最终一致性和补偿机制。

### 4.3 故障可能级联传播

订单调用商品，商品调用库存。如果库存变慢，上游线程可能持续等待，最终造成订单服务线程耗尽。

### 4.4 调试和排查更难

一次请求可能穿过多个服务。没有统一日志、TraceId 和监控时，很难知道请求在哪一层变慢或失败。

### 4.5 部署和配置更复杂

服务数量增加后，需要管理端口、环境变量、配置文件、依赖启动顺序、健康状态和服务版本。

### 4.6 接口兼容成本增加

服务之间通过接口通信。接口字段的新增、删除和含义变化都需要考虑调用方兼容性，不能像修改同一个工程里的私有方法一样随意。

## 五、CloudMall 的服务边界设计

本学习路线使用 `CloudMall` 作为贯穿全程的实战项目。优先级 1 先建立最小服务骨架，后续再逐步加入注册中心、网关、认证、容错、事务、消息和观测能力。

### 5.1 初始服务划分

| 服务 | 主要职责 | 不负责的内容 | 初始数据边界 |
| --- | --- | --- | --- |
| `user-service` | 用户资料、用户状态、用户基础查询 | 订单创建、商品库存、支付扣款 | 用户表、用户地址等 |
| `product-service` | 商品基本信息、分类、上下架状态 | 订单流程、支付、用户登录 | 商品表、分类表等 |
| `order-service` | 订单创建、订单状态和订单查询 | 商品主数据维护、账户扣款实现 | 订单表、订单明细表等 |
| `common` | 共享的基础响应结构、通用异常码、通用工具 | 业务实体、业务规则、数据库访问 | 不直接拥有业务数据 |

### 5.2 服务边界的三个判断问题

设计一个服务时，至少回答下面三个问题：

1. 这个服务对哪类业务数据拥有最终解释权？
2. 哪些业务规则必须由这个服务保证？
3. 其他服务需要什么能力，应该通过什么接口获得？

如果多个服务都直接修改同一张业务表，通常说明服务边界还没有真正建立。

### 5.3 `common` 模块应该放什么

可以放入 `common` 的内容：

- 统一响应结构，例如 `Result<T>`。
- 通用分页对象。
- 通用错误码定义。
- 基础异常类。
- 与业务无关的工具类。
- 通用的序列化或日期处理配置。

不建议放入 `common` 的内容：

- 用户、商品、订单等业务实体。
- 任意服务的 Mapper、Repository 或数据库配置。
- 只被一个服务使用的业务工具。
- 为了省事而共享的业务规则。

`common` 的目标是减少重复基础代码，而不是把所有代码重新集中成一个“公共大模块”。

## 六、推荐的项目目录

```text
spring-cloud-demo/
├── pom.xml                         # Maven 父工程，只负责聚合和统一版本
├── README.md                       # 项目说明、架构图和启动方式
├── .gitignore
├── common/
│   ├── pom.xml
│   └── src/main/java/.../common/
├── user-service/
│   ├── pom.xml
│   └── src/
│       ├── main/java/.../user/
│       └── main/resources/application.yml
├── product-service/
│   ├── pom.xml
│   └── src/
│       ├── main/java/.../product/
│       └── main/resources/application.yml
└── order-service/
    ├── pom.xml
    └── src/
        ├── main/java/.../order/
        └── main/resources/application.yml
```

### 6.1 根 `pom.xml` 的职责

根工程建议使用 `pom` 打包类型，只负责：

- 聚合子模块。
- 统一 Java 版本。
- 统一 Spring Boot 等依赖版本。
- 统一插件版本和编码配置。

根工程不应该包含具体业务代码。

示意结构如下：

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.wwweinuo</groupId>
    <artifactId>spring-cloud-demo</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <packaging>pom</packaging>

    <modules>
        <module>common</module>
        <module>user-service</module>
        <module>product-service</module>
        <module>order-service</module>
    </modules>
</project>
```

具体 Spring Boot、Spring Cloud 和 JDK 版本应在整个项目中统一，不要让每个子模块自行选择版本。

### 6.2 子模块的职责

每个业务服务都应当能够独立编译和启动。一个服务内部可以先保持简单，但至少要有自己的：

- 启动类。
- 配置文件。
- Controller。
- Service。
- 数据访问层占位或基础实现。
- 服务自己的测试代码。

优先级 1 不要求服务之间完成远程调用。远程调用会在 OpenFeign 阶段实现；本阶段先验证模块边界和独立启动能力。

## 七、服务独立启动配置

本阶段可以使用固定端口和本地配置，让服务先稳定运行起来：

### `user-service/src/main/resources/application.yml`

```yaml
server:
  port: 8081

spring:
  application:
    name: user-service
```

### `product-service/src/main/resources/application.yml`

```yaml
server:
  port: 8082

spring:
  application:
    name: product-service
```

### `order-service/src/main/resources/application.yml`

```yaml
server:
  port: 8083

spring:
  application:
    name: order-service
```

`spring.application.name` 在本阶段主要用于标识服务。进入 Nacos 阶段后，它还会参与服务注册、发现和配置定位。

## 八、初始接口和业务边界

本阶段先定义接口边界，不急于实现跨服务调用。

| 服务 | 方法 | 路径 | 含义 |
| --- | --- | --- | --- |
| user-service | `GET` | `/users/{id}` | 查询用户基础信息 |
| product-service | `GET` | `/products/{id}` | 查询商品基础信息 |
| order-service | `POST` | `/orders` | 创建订单 |
| order-service | `GET` | `/orders/{id}` | 查询订单详情 |

订单创建需要用户和商品信息，但本阶段只记录“订单服务依赖用户服务和商品服务”这一架构事实，不直接把三个服务合并成一个模块，也不直接访问对方数据库。

## 九、一次请求的两种形态

### 9.1 单体中的订单请求

```text
客户端
  ↓
订单 Controller
  ↓
订单 Service
  ├── 用户模块方法调用
  ├── 商品模块方法调用
  └── 订单数据访问
        ↓
      MySQL
```

特点：调用通常发生在同一个进程内，事务和异常传播相对容易处理。

### 9.2 微服务中的订单请求

优先级 1 只展示目标形态，暂不实现后续治理组件：

```text
客户端
  ↓
order-service
  ├── 远程调用 user-service
  ├── 远程调用 product-service
  └── 访问订单自己的数据

后续再加入：
  ├── Nacos：服务发现与配置
  ├── OpenFeign：声明式远程调用
  ├── Gateway：统一入口
  ├── Sentinel：故障治理
  ├── Seata / MQ：数据一致性
  └── Prometheus / Trace：可观测性
```

核心变化是：模块之间不再只是方法调用，而是通过网络、接口和独立进程协作。

## 十、实践步骤

### 步骤 1：确认项目基础约束

在开始编码前，先确定：

- 使用的 JDK 版本。
- Spring Boot、Spring Cloud 的版本组合。
- 包名规范，例如 `com.wwweinuo`。
- 服务命名规范，例如 `user-service`。
- 端口分配规则。
- Git 分支和提交规范。

这些内容写入项目根目录的 `README.md`，避免后续每个服务各自决定。

### 步骤 2：创建 Maven 父工程

完成根 `pom.xml`，确认打包类型为 `pom`，并声明三个子模块。

验证命令：

```bash
mvn clean validate
```

### 步骤 3：创建 `common` 模块

先只放一个最小的通用响应结构或错误码，验证业务服务能够依赖它。

不要在这个阶段把用户实体、商品实体和订单实体都放进 `common`。

### 步骤 4：创建三个业务服务

每个服务都创建自己的启动类和配置文件，保证它们能够独立运行。

可以为每个服务增加一个最小接口：

```java
@RestController
public class ServiceInfoController {

    @GetMapping("/internal/info")
    public String info() {
        return "user-service";
    }
}
```

商品和订单服务只需要返回各自的服务名，用于确认端口和进程没有串错。

### 步骤 5：分别启动并验证

验证三个端口能够独立访问：

```bash
curl http://localhost:8081/internal/info
curl http://localhost:8082/internal/info
curl http://localhost:8083/internal/info
```

预期结果分别对应：

```text
user-service
product-service
order-service
```

### 步骤 6：记录服务边界

在 README 中补充：

- 每个服务的职责。
- 每个服务拥有的数据。
- 服务之间的依赖关系。
- 当前阶段没有实现的能力。
- 后续引入组件的原因。

### 步骤 7：完成一次故障思考实验

本阶段暂不需要实现熔断，但要完成一次架构推演：

1. 假设 `product-service` 不可用。
2. 订单创建是否还能继续？
3. 如果不能继续，客户端会看到什么？
4. 如果强行重试，可能造成什么问题？
5. 后续应该由哪个组件负责超时、熔断或降级？

把结论写入 `docs/故障实验记录.md` 或 README，作为后续 Sentinel 学习的起点。

## 十一、常见错误和改进方式

### 11.1 按数据库表拆服务

错误方式：一张表一个服务，服务之间没有业务边界。

改进方式：围绕业务能力和数据所有权拆分。服务应当能够独立解释和维护自己的业务规则。

### 11.2 所有服务共享一套业务数据库

错误方式：每个服务都直接查询和修改其他服务的表。

问题：服务边界只是目录上的边界，任何修改都可能绕过业务规则。

改进方式：服务拥有自己的数据。即使早期使用同一个 MySQL 实例，也至少使用独立的库或明确的表所有权；跨服务数据通过接口或消息获得。

### 11.3 `common` 模块变成公共大杂烩

错误方式：所有实体、Mapper、业务方法都放入 `common`，导致服务再次紧密耦合。

改进方式：`common` 只放真正稳定、与具体业务无关的基础代码。

### 11.4 一开始就引入所有中间件

错误方式：同时配置 Nacos、Gateway、Feign、Sentinel、Seata、Redis、MQ、监控和 Docker，但不知道每个组件解决什么问题。

改进方式：先完成独立服务骨架，再按问题逐个引入组件。每引入一个组件，都记录“问题、方案、实验、结果”。

### 11.5 只画漂亮架构图，不验证服务能启动

错误方式：文档中的架构很完整，但三个服务无法分别编译和运行。

改进方式：架构图必须对应可运行的模块、端口和接口。先验证最小闭环，再逐步增加能力。

### 11.6 过早追求复杂的领域建模

错误方式：在还没有理解服务边界前，就设计大量复杂的领域对象和抽象层。

改进方式：本阶段先把职责、数据所有权、接口和启动骨架做清楚，复杂业务模型留到对应业务实现阶段。

1. 什么是微服务？它和传统分层架构有什么区别？

3. 单体架构什么时候反而更合适？

1. 用户、商品、订单为什么可以拆成三个服务？
2. 服务边界应该依据什么划分？
3. 为什么不建议服务之间直接共享业务表？

1. Maven 多模块父工程和业务子模块分别负责什么？

1. 商品服务不可用时，订单服务应该如何处理？
