# 4-LoadBalancer 实例选择与调用稳定性

> 本文是《Java 后端微服务学习计划》的优先级 4 专题。

## 一、本阶段学习目标

- 区分服务发现和负载均衡。
- 解释 `lb://service-name` 的调用链路。
- 启动多个同名服务实例并观察请求分流。
- 理解实例列表、选择策略、缓存和健康状态。
- 说明重试与负载均衡的关系及写请求风险。

## 二、服务发现不等于负载均衡

Nacos 服务发现解决的是“有哪些实例”：

```text
product-service
├── 127.0.0.1:8082
└── 127.0.0.1:8084
```

LoadBalancer 解决的是“本次请求选择哪一个实例”：

```text
请求 1 → 8082
请求 2 → 8084
请求 3 → 8082
```

在 OpenFeign 或 Gateway 中看到 `product-service` 时，客户端先根据服务名获得实例列表，再交给 LoadBalancer 选择目标地址。

## 三、调用链路

```text
订单服务
  ↓ Feign: product-service
Spring Cloud LoadBalancer
  ↓ 查询服务实例
Nacos
  ↓ 返回实例列表
选择一个健康实例
  ↓
http://127.0.0.1:8082/products/1
```

如果服务只有一个实例，负载均衡仍然会工作，只是没有分流效果。服务注册成功也不代表远程调用一定成功，网络、端口、接口、权限和数据库都可能导致调用失败。

## 四、CloudMall 多实例实验

商品服务当前默认端口为 `8082`。可以额外启动一个端口为 `8084` 的实例：

```bash
mvn -pl product-service spring-boot:run -Dspring-boot.run.arguments="--server.port=8084"
```

两个实例都使用同一个 Nacos 服务名 `product-service`，但端口不同。商品 Controller 已输出实例端口日志：

```text
商品服务实例 port=8082 收到请求，productId=1
商品服务实例 port=8084 收到请求，productId=1
```

连续访问网关接口：

```bash
curl http://localhost:8000/api/products/1
curl http://localhost:8000/api/products/1
curl http://localhost:8000/api/products/1
```

同时观察两个商品服务的控制台，记录每次请求由哪个实例处理。不要只凭一次请求判断策略，需要连续请求并记录结果。

## 五、实例下线实验

1. 启动商品服务 `8082` 和 `8084`。
2. 确认两个实例都出现在 Nacos 的 `dev` 命名空间。
3. 停止 `8084` 实例。
4. 继续访问商品接口。
5. 观察 Nacos 实例状态和调用结果。

需要区分两个时间点：

- Nacos 发现实例变更的时间。
- LoadBalancer 本地实例列表和缓存更新的时间。

在短暂不一致期间，可能出现一次调用仍然命中已停止实例。生产环境要结合健康检查、合理缓存和超时配置降低影响。

## 六、重试边界

重试可以改善偶发网络错误，但也会带来额外请求：

```text
一次失败请求
  ↓ 重试
两次请求
  ↓ 多实例并发下放大
更多下游负载
```

查询类请求通常比创建订单更适合有限重试。订单创建、扣库存和扣余额等写操作必须先设计幂等，再决定是否允许重试。不能把“失败就重试”作为通用故障处理方案。

## 九、下一阶段衔接

LoadBalancer 解决实例选择，但客户端仍然需要知道每个服务的地址和接口。Gateway 将把客户端入口统一起来，集中处理路由、过滤器、跨域和入口治理。
