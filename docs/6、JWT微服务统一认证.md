# 6-JWT 微服务统一认证

> 本文是《Java 后端微服务学习计划》的优先级 6 专题。

## 一、本阶段学习目标

- 区分认证和授权。
- 理解登录、签发 JWT、网关校验和下游授权的链路。
- 认识 JWT 的组成、过期时间和签名校验。
- 建立外部 Header 与内部可信用户上下文的边界。
- 设计未登录、Token 过期、Token 篡改和权限不足的处理方式。

## 二、微服务为什么需要统一认证

如果每个服务单独实现登录和 Token 校验，会导致：

- 认证规则重复。
- 密钥和过期策略不一致。
- 每个服务都要暴露登录相关接口。
- 客户端需要理解多个服务的认证方式。

更清晰的入口链路是：

```text
客户端登录
  ↓
Auth Service 签发 JWT
  ↓
客户端携带 Authorization: Bearer <token>
  ↓
Gateway 校验签名和有效期
  ↓
传递可信用户上下文
  ↓
下游服务进行资源级授权
```

## 三、认证和授权的区别

| 概念 | 需要回答的问题 | 示例 |
| --- | --- | --- |
| 认证 Authentication | 你是谁？ | Token 属于用户 1 |
| 授权 Authorization | 你能做什么？ | 用户 1 是否能修改订单 100 |

Gateway 可以统一做基础认证，但不能替代下游业务授权。订单服务仍然要判断订单是否属于当前用户，管理员接口仍然要检查角色或权限。

## 四、JWT 结构

JWT 通常由三段组成：

```text
Header.Payload.Signature
```

常见 Claims 包括：

| Claim | 含义 |
| --- | --- |
| `sub` | 主体标识，例如用户 ID |
| `iat` | 签发时间 |
| `exp` | 过期时间 |
| `iss` | 签发者 |
| `roles` | 角色信息，可按项目需要使用 |

JWT 的 Payload 只是编码，不是加密。不要把密码、身份证号或其他敏感数据直接放入 Token。签名密钥必须通过安全配置注入，不能提交到 Git。

## 五、推荐的 CloudMall 实践顺序

### 步骤 1：先设计登录结果

```json
{
  "token": "eyJ...",
  "expiresIn": 3600
}
```

### 步骤 2：Gateway 校验 Token

校验至少包括：

- 是否存在 `Authorization` Header。
- 是否使用 `Bearer` 格式。
- 签名是否正确。
- 是否过期。
- 签发者和必要 Claims 是否符合约定。

### 步骤 3：传递内部用户上下文

网关校验后，可以把用户 ID 传给下游。但外部客户端可以伪造同名 Header，因此网关必须先删除外部传入的内部 Header，再写入校验后的值。例如：

```text
外部 X-User-Id      → 先删除
Token 的 subject    → 网关校验后写入 X-User-Id
```

下游服务只能在可信网络边界内信任这个 Header，并应通过网络策略限制客户端绕过 Gateway 直接访问业务服务。

### 步骤 4：下游进行业务授权

```text
Gateway：Token 合法，用户是 1
Order Service：订单 100 是否属于用户 1？
```

## 六、安全实验

### 实验 1：无 Token

访问需要认证的接口，预期返回 `401 Unauthorized`，并且请求不会到达业务 Controller。

### 实验 2：Token 过期

使用过期 Token 访问接口，确认 Gateway 拒绝请求，而不是把过期用户传给下游。

### 实验 3：伪造内部 Header

客户端携带 `X-User-Id: 999`，但 Token 属于用户 1。确认 Gateway 不直接信任外部 Header。

### 实验 4：认证通过但无权限

用户登录成功后访问不属于自己的订单，预期是 `403 Forbidden` 或明确的业务拒绝，而不是 `401`。

## 七、常见错误

- 把 JWT 当成加密数据，向 Payload 中放敏感信息。
- 只在 Gateway 校验 Token，却不在下游做资源授权。
- 允许客户端直接传递并覆盖内部用户 Header。
- 把永不过期的 JWT 当成登出方案。
- 将签名密钥硬编码在配置文件并提交到仓库。
- 把认证失败和业务无权限都返回成同一个状态。
