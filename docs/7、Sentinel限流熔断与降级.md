# 7-Sentinel 限流、熔断与降级

> 本文是《Java 后端微服务学习计划》的优先级 7 专题。

## 一、本阶段学习目标

- 区分限流、熔断、降级和系统保护。
- 理解慢调用如何沿调用链传播并形成雪崩。
- 使用 Sentinel 为入口和远程调用设置保护规则。
- 设计可理解的降级结果，而不是简单吞掉异常。
- 认识规则阈值、统计窗口和恢复时间的关系。

## 二、为什么需要故障治理

假设订单服务同步调用商品服务：

```text
大量客户端请求
  ↓
订单服务线程被占用
  ↓ 商品服务变慢
等待和超时增加
  ↓
订单服务资源耗尽
  ↓
整个调用链不可用
```

微服务故障往往不是单点停止，而是慢调用、连接占满、重试放大和线程耗尽逐步传播。Sentinel 通过流量控制和依赖保护降低传播范围。

## 三、核心概念

### 7.1 限流

控制单位时间内允许通过的请求量，保护服务不被突发流量压垮。

```text
超过阈值 → 快速拒绝或排队
```

限流不代表下游故障，它主要解决“请求太多”。

### 7.2 熔断

当依赖服务持续慢或持续失败时，暂时停止向依赖发送请求：

```text
CLOSED → OPEN → HALF_OPEN → CLOSED
```

- `CLOSED`：正常调用并统计结果。
- `OPEN`：快速失败，不再访问下游。
- `HALF_OPEN`：放少量探测请求。
- 探测成功：回到 `CLOSED`；失败：重新 `OPEN`。

### 7.3 降级

请求无法正常完成时返回备用结果或明确提示。降级结果必须符合业务语义，不能把“商品不存在”和“商品服务超时”混成同一类结果。

## 四、规则设计思路

| 保护对象 | 规则示例 | 目的 |
| --- | --- | --- |
| Gateway 路由 | 每秒最多 100 个请求 | 保护统一入口 |
| 订单创建 | 每秒最多 20 个请求 | 保护写入链路 |
| 商品查询 | 慢调用比例超过阈值 | 避免拖垮订单服务 |
| 热点商品 ID | 单个商品限制并发 | 保护热点数据 |
| 系统 CPU | CPU 过高时降低流量 | 系统级保护 |

阈值不能只凭感觉设置，应结合压测、平均延迟、峰值流量、线程池和数据库连接池容量确定。

## 五、CloudMall 实践路线

1. 先对商品查询增加可控延迟开关。
2. 只保护订单创建或商品查询一个资源。
3. 先验证限流，再验证慢调用熔断。
4. 记录正常结果、限流结果、熔断结果和恢复结果。
5. 再决定是否把规则持久化到 Nacos。

可以把测试开关放入 Nacos，例如：

```yaml
cloudmall:
  experiment:
    product-delay-ms: 0
```

实验配置和业务生产配置要分开管理，避免把故障开关误留在生产环境。

## 六、故障实验

### 实验 1：入口限流

使用脚本在短时间发送大量商品查询请求，观察：

- 通过请求数量。
- 被拒绝请求数量。
- 服务 CPU、线程和数据库连接变化。
- 客户端收到的状态码和响应体。

### 实验 2：慢调用熔断

让商品服务延迟超过订单服务的读取超时时间，连续创建订单，观察订单服务是否快速失败，以及熔断后是否减少对商品服务的请求。

### 实验 3：半开恢复

恢复商品服务，等待熔断窗口结束，观察探测请求和状态转换。记录从 `OPEN` 到 `CLOSED` 的条件。

## 七、重试和熔断不能叠加失控

如果上游、Feign、LoadBalancer 和网关都配置重试，一次用户请求可能变成多次下游请求：

```text
1 次入口请求 × 3 次 Feign 重试 × 2 个下游层级 = 可能的多倍流量
```

写请求还可能被重复执行。必须统一重试边界，并结合幂等键和请求类型设计。

## 九、下一阶段衔接

限流和熔断只能控制失败影响，不能自动恢复跨服务已经完成的部分操作。订单、库存和账户跨库时，需要研究分布式事务和最终一致性。
