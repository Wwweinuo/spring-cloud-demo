# 8-Seata 分布式事务与一致性

> 本文是《Java 后端微服务学习计划》的优先级 8 专题。

## 一、本阶段学习目标

- 解释本地事务为什么不能覆盖多个服务和数据库。
- 理解 Seata 中 TC、TM、RM 的角色。
- 区分 AT、TCC、Saga 和 XA 的适用场景。
- 设计回滚、重试、补偿和人工介入路径。
- 认识分布式事务带来的锁、性能、可用性和运维成本。

## 二、本地事务的边界

单体应用中的一个 `@Transactional` 通常可以覆盖同一个数据源中的多张表：

```text
订单表 + 库存表 + 账户表
        ↓
同一数据库本地事务
```

拆成服务后，订单、库存和账户可能位于不同进程、不同数据库：

```text
Order Service → Order DB
      ↓
Inventory Service → Inventory DB
      ↓
Payment Service → Payment DB
```

订单服务上的本地事务无法回滚已经在库存服务或账户服务提交的操作。

## 三、Seata 角色

```text
业务调用方 / TM
        ↓ 开启全局事务
       TC  ← 协调全局事务
        ↑
各服务 RM → 执行分支事务并报告状态
```

- TC：事务协调者，管理全局事务和分支事务。
- TM：事务管理者，发起、提交或回滚全局事务。
- RM：资源管理者，管理本地资源和分支事务。

## 四、事务模式比较

| 模式 | 基本机制 | 适合场景 | 主要代价 |
| --- | --- | --- | --- |
| AT | 代理本地事务并记录回滚信息 | 表结构规则清晰的 CRUD | 依赖数据库和回滚日志 |
| TCC | Try、Confirm、Cancel 业务补偿 | 可明确拆分预留和确认 | 需要编写三套业务逻辑 |
| Saga | 一步一步执行并定义反向补偿 | 长流程、长事务 | 补偿逻辑复杂 |
| XA | 数据库/资源参与两阶段提交 | 强一致要求高的短事务 | 锁时间长、性能和可用性成本高 |

不要因为“用了 Seata”就默认所有流程都应该使用全局事务。能通过本地事务、可靠消息或业务补偿解决的问题，不一定需要强事务协调。

## 五、CloudMall 业务实验

目标流程：

```text
创建订单
  ↓
扣减库存
  ↓
扣减余额
  ↓
确认订单
```

先人为制造以下故障：

```text
订单写入成功
库存扣减成功
余额扣减失败
```

记录三种处理方式：

1. 不处理：产生数据不一致。
2. 全局回滚：已提交分支尝试回滚。
3. 最终一致性：记录待补偿状态，由任务或消息重试。

当前项目的四张业务表仍由各自服务负责。接入 Seata 前，应先增加库存、账户等服务和独立数据边界，不要让订单服务直接操作其他服务的表。

## 六、AT 模式需要关注的内容

- 每个参与事务的数据库准备对应的 `undo_log`。
- 事务分组和 TC 地址必须正确。
- 分支事务提交后仍可能受全局锁影响。
- 回滚依赖前后镜像和可逆的数据变更。
- DDL、长事务和复杂 SQL 需要单独验证。

示意配置：

```yaml
seata:
  enabled: true
  tx-service-group: cloudmall-tx-group
  service:
    vgroup-mapping:
      cloudmall-tx-group: default
```

实际地址、注册中心和版本配置必须与部署的 Seata Server 保持一致，不要直接复制示例到生产环境。

## 七、故障实验

### 实验 1：中途失败

在扣库存成功后让扣余额接口失败，观察全局事务、订单状态和库存状态。

### 实验 2：网络中断

在一个分支提交后断开调用方网络，判断协调者如何处理未知结果，以及业务是否需要查询和补偿。

### 实验 3：重复补偿

让补偿任务执行两次，确认恢复库存、退款等操作具备幂等性。
