# 9-Redis 缓存、锁与幂等

> 本文是《Java 后端微服务学习计划》的优先级 9 专题。

## 一、本阶段学习目标

- 设计商品详情等热点数据的缓存。
- 理解缓存穿透、击穿、雪崩和数据不一致。
- 使用幂等键避免重复下单、重复消费和重复扣减。
- 理解分布式锁的适用边界、过期和续期。
- 认识缓存和锁都不能替代数据库事务。

## 二、Redis 在微服务中的位置

```text
Gateway / 业务服务
        ↓
      Redis
   ┌────┼────┐
 缓存  锁   幂等记录
        ↓
      MySQL
```

Redis 适合保存短生命周期、高访问频率或需要快速判断的数据，但业务最终正确性仍应由数据库约束、事务和状态机保证。

## 三、缓存设计

商品详情缓存示例：

```text
Key: cloudmall:product:detail:1
Value: 商品详情 JSON
TTL: 5 分钟
```

读取流程：

```text
查询商品
  ↓
读取 Redis
  ├── 命中 → 返回缓存
  └── 未命中 → 查 MySQL → 写入 Redis → 返回
```

Key 应包含业务前缀、对象类型和 ID，避免不同服务互相覆盖。缓存 Value 不要直接复用数据库实体作为跨服务契约。

## 四、四类缓存问题

| 问题 | 成因 | 常见处理 |
| --- | --- | --- |
| 穿透 | 大量查询不存在的数据 | 参数校验、空值缓存、布隆过滤器 |
| 击穿 | 热点 Key 同时过期 | 互斥重建、逻辑过期、预热 |
| 雪崩 | 大量 Key 同时失效或 Redis 故障 | TTL 随机化、分批失效、本地降级 |
| 不一致 | 数据库已修改但缓存仍旧 | 更新策略、短 TTL、删除后异步重建 |

缓存更新策略必须结合业务一致性要求。商品价格和库存比商品描述更敏感，不能使用完全相同的缓存策略。

## 五、幂等设计

幂等的目标是：同一个业务请求重复执行，最终结果和执行一次一致。

订单创建可以要求客户端携带幂等键：

```text
Idempotency-Key: order-request-abc123
```

服务端流程：

```text
收到幂等键
  ↓
Redis SETNX / 数据库唯一索引占位
  ├── 首次请求 → 执行业务
  └── 已存在 → 返回原结果或处理中状态
```

必须明确幂等记录的状态：`PROCESSING`、`SUCCESS`、`FAILED`。不能把“已经收到请求”简单等同于“订单创建成功”。

## 六、分布式锁

适合使用锁控制同一资源的并发修改，例如同一商品的库存预扣。锁 Key 示例：

```text
cloudmall:lock:product:1
```

锁必须满足：

- 加锁和释放锁具有唯一持有者标识。
- 设置过期时间，避免进程崩溃后永久占用。
- 业务执行时间可能超过 TTL 时需要可靠续期机制。
- 释放锁时校验持有者，不能删除其他线程的新锁。
- 关键正确性仍由数据库条件更新和唯一约束兜底。

Redisson 可以简化锁和续期，但不代表可以忽略事务、超时和故障实验。

## 七、故障实验

### 实验 1：缓存命中

连续查询商品详情，观察第一次访问数据库、后续访问 Redis，并验证更新商品后缓存何时变化。

### 实验 2：热点 Key 过期

将一个商品缓存 TTL 调得很短，使用并发请求观察是否出现大量回源数据库。

### 实验 3：重复创建订单

用同一个 `Idempotency-Key` 连续发送订单请求，确认不会创建两笔订单。

### 实验 4：锁持有进程异常

持锁后强制终止服务，确认锁最终能够过期；再验证误释放其他实例锁的问题不会发生。
