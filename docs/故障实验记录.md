## 三、实验 1：Nacos 未启动

### 3.1 复现步骤

先确认 Nacos 正在运行：

```powershell
docker ps --filter "name=nacos-standalone"
```

停止 Nacos：

```powershell
docker stop nacos-standalone
```

然后启动一个或多个 Spring Boot 服务，观察服务启动日志。实验结束后恢复 Nacos：

```powershell
docker start nacos-standalone
```

### 3.2 当前项目预期现象

1. Spring Boot 服务仍可能启动，因为配置导入使用了 `optional:nacos:`。
2. Nacos Config 客户端会出现连接失败、超时或重试日志。
3. 服务不能成功注册到 Nacos，也不能从 Nacos 获取最新配置。
4. 本地 `application-*.yml` 中的数据库和端口配置仍可以作为启动配置。
5. 如果业务配置只存在于 Nacos，本地没有对应兜底值，则业务功能可能出现配置缺失。

### 3.3 实验结论

`optional:nacos:` 可以避免配置中心暂时不可用时直接阻止应用启动，但它不能保证服务注册和远程配置读取成功。生产环境是否允许继续启动，需要根据配置的重要程度决定：数据库地址、密钥等关键配置不应该静默使用错误的默认值。

## 四、实验 2：Data ID 配置错误

### 4.1 复现步骤

以 `user-service` 为例，将开发环境配置导入临时改成不存在的 Data ID：

```yaml
spring:
  config:
    import:
      - optional:nacos:user-service-not-found.yaml?group=DEFAULT_GROUP&refreshEnabled=true
```

重新启动 `user-service`，观察日志和接口：

```powershell
Invoke-RestMethod http://localhost:8081/internal/nacos-config
```

实验结束后恢复为：

```text
user-service-dev.yaml
```

### 4.2 当前项目预期现象

日志会出现类似内容：

```text
[Nacos Config] config[dataId=user-service-not-found.yaml, group=DEFAULT_GROUP] is empty
```

由于当前使用 `optional:nacos:`，服务通常可以继续启动。新增的配置验证接口会返回：

```text
NOT_FOUND
```

### 4.3 实验结论

Data ID 是配置定位的一部分。Data ID 拼写错误、扩展名不一致或环境名称不一致，都会导致配置读取不到。当前项目使用 `.yaml`，不能把 Nacos 中的配置名称写成 `.yml` 后再期待它自动匹配。

如果某项配置是应用启动所必需的，不应使用 `optional:nacos:` 掩盖错误，而应该让应用快速失败并提示配置问题。

## 五、实验 3：Namespace 配置错误

### 5.1 复现步骤

临时将某个服务的 Nacos 命名空间改成不存在或不正确的值，例如：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        namespace: wrong-namespace
      config:
        namespace: wrong-namespace
```

重新启动服务，观察 Nacos 配置读取、服务注册和日志信息。实验结束后恢复：

```yaml
namespace: ${NACOS_NAMESPACE:dev}
```

### 5.2 当前项目预期现象

1. 配置中心会在错误的命名空间中查找 Data ID。
2. 即使 `dev` 命名空间存在正确配置，服务也会读取不到它。
3. 服务发现会将实例注册到错误的命名空间，导致 `dev` 命名空间中的调用方无法发现它。
4. 配置接口通常返回 `NOT_FOUND`，或使用本地配置中的默认值。

日志中应重点关注命名空间信息，例如：

```text
Config-fixed-dev-localhost_8848
tenant=dev
```

### 5.3 实验结论

Namespace 同时影响配置中心和服务发现，但二者的配置项彼此独立：

```yaml
spring.cloud.nacos.config.namespace
spring.cloud.nacos.discovery.namespace
```

当前项目通过同一个 `NACOS_NAMESPACE` 环境变量统一设置为 `dev`，可以避免两个模块使用不同命名空间。

还需要注意：Nacos 控制台显示的命名空间名称不一定等于命名空间 ID。客户端配置必须使用 Namespace ID。

## 六、实验 4：服务实例下线

### 6.1 复现步骤

先确认三个服务已经注册在 Nacos 的 `dev` 命名空间中。然后停止其中一个服务，例如停止 `product-service` 的 Java 进程。

停止后观察：

1. Nacos 控制台中的实例状态。
2. 服务实例是否变为不健康或被移除。
3. 直接访问服务端口的结果：

```powershell
Invoke-RestMethod http://localhost:8082/internal/info
```

恢复服务后再次观察实例是否重新注册。

### 6.2 当前项目现象

当前订单服务已经接入 OpenFeign。直接访问已经停止的 `product-service` 端口时，客户端会收到连接失败；通过订单创建接口间接调用商品服务时，Feign 会在连接或读取超时后抛出远程调用异常，订单服务的全局异常处理器会返回“下游服务暂时不可用，请稍后重试”。

服务重新启动后，Nacos 客户端会重新注册实例，控制台应重新显示对应的服务实例和端口。

### 6.3 进入 OpenFeign 后的风险

当 `order-service` 通过服务名调用 `product-service` 后，下游实例下线会引发：

- 连接失败。
- 请求超时。
- 上游线程等待和资源占用。
- 盲目重试导致重复业务操作。
- 多级调用产生级联故障。

因此，服务注册只负责发现实例，不能自动解决超时、重试、熔断和降级问题。

## 七、实验 5：配置动态刷新

### 7.1 实验配置

以 `user-service` 为例，在 Nacos 的 `dev` 命名空间、`DEFAULT_GROUP` 分组下创建：

```text
Data ID: user-service-dev.yaml
```

配置内容：

```yaml
cloudmall:
  greeting: hello from nacos
```

### 7.2 实测步骤

启动 `user-service`，访问配置查询接口：

```powershell
Invoke-RestMethod http://localhost:8081/internal/nacos-config
```

确认接口能够返回 Nacos 中的配置值。然后在 Nacos 控制台修改 `cloudmall.greeting` 并发布，再次访问相同接口。

### 7.3 实测结果

配置修改并发布后，接口能够读取到新的配置值，不需要重启 `user-service`，说明以下链路已经验证成功：

```text
Nacos 配置发布
    ↓
Nacos 客户端监听
    ↓
Spring Cloud 配置刷新
    ↓
@RefreshScope 重建 ServiceInfoController
    ↓
/internal/nacos-config 返回新值
```

### 7.4 实验结论

动态刷新适合开关、提示语、部分运行参数等可以安全变更的配置。数据库地址、访问密钥、核心基础设施地址等配置不应为了动态刷新而随意修改，发布前需要考虑连接重建、数据安全和回滚问题。

## 八、OpenFeign 下的商品边界不可用推演

当前 `user-service`、`product-service`、`order-service` 是独立进程。订单服务已经通过 OpenFeign 使用服务名调用用户服务和商品服务，不直接访问对方数据库。订单创建请求中的 `productName` 和 `unitPrice` 仅为兼容旧请求保留，实际以商品服务返回的名称和价格为准。

如果商品服务不可用，订单服务会遇到连接失败或超时。当前配置连接超时为 2 秒、读取超时为 3 秒，异常会被转换为可理解的业务失败响应；盲目重试仍可能造成重复业务操作或放大下游压力。

后续治理方向：

- 超时控制：限制单次远程调用最长等待时间。
- Sentinel：限流、熔断和降级。
- 幂等设计：避免重试造成重复写入。
- Trace 和统一日志：定位跨服务请求的失败位置。

## 九、本阶段结论

通过以上实验可以得到：

1. Nacos 注册中心负责服务实例发现，不能代替配置中心的配置管理能力。
2. Nacos 配置的定位依赖 Namespace、Group 和 Data ID，三者必须完全匹配。
3. `optional:nacos:` 提高了本地开发环境的容错性，但也可能掩盖关键配置缺失。
4. 配置动态刷新需要配置监听和可刷新的 Bean 配合，不能仅凭“发布成功”判断应用已经使用新值。
5. 服务注册成功不代表服务间调用一定可靠，OpenFeign 仍需要超时、重试边界、熔断、降级和幂等设计。

Nacos 阶段的配置和故障实验已经完成，当前进入下一阶段：验证 OpenFeign 让 `order-service` 通过服务名调用 `user-service` 和 `product-service`。
